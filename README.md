# oechsner.dev

Personal portfolio and blog for Jonas Öchsner. **SvelteKit**, fully prerendered, deployed to
**Cloudflare Pages** through Cloudflare's own Git integration — no API tokens, no deploy
credentials anywhere.

The visual design is specified in [`DESIGN.md`](DESIGN.md) and derived from the
[Elevate portfolio template](https://dribbble.com/shots/20829830-Portfolio-Template-Elevate)
by Gaël Duval. **Read DESIGN.md before changing any styling** — it is the contract the CSS
implements, including the rule that no component may hard-code a colour.

**The site leads with the writing, not the author.** `/` is the post index; the newest post's
title takes the largest type on the site. The portfolio is a complete page at `/about`, one
click from anywhere, but it does not lead. `DESIGN.md` §11 states the rule and what depends on
it — read it before moving anything above the fold.

## Writing a post

Add a file to `src/posts/`. The date prefix keeps the folder sorted and is stripped from the
URL, so `2026-09-01-a-thing.svx` publishes at `/blog/a-thing`.

```yaml
---
title: A thing I learned          # required — the build fails without it
date: '2026-09-01'                # required
summary: One or two sentences. Shown on the index and in link previews.
tags: ['pytorch', 'systems']
cover: /img/a-thing/cover.svg     # optional; omit and the row runs full width
coverAlt: Description for screen readers
draft: true                       # optional — hidden in production, visible in dev
---
```

Read time is computed at build time from the word count; it is not a front-matter field.
Because posts are `.svx`, a post can `import` and render a Svelte component inline when prose
isn't enough.

```sh
git add src/posts && git commit -m "post: a thing I learned" && git push
```

Cloudflare builds and deploys. That's the whole publishing flow.

## Local development

```sh
npm install
npm run dev       # Vite dev server
npm run build     # type-checks Worker bindings, then builds
npm run preview   # serves the real Pages output via `wrangler pages dev`
npm run check     # svelte-check — what CI runs
npm run cv        # recompiles static/resume-en.pdf from resume.tex
npm run og        # rasterises each static/img/<postname>/cover.svg to .png for link previews
```

`npm run og` matters more than it looks: social platforms reject SVG for `og:image`, so a
shared link previews with no image unless a PNG exists beside each SVG. Re-run it (and commit
the PNGs) whenever you add or change a cover image. It needs `playwright` — `npm i -D playwright`
if it isn't there.

### Updating the CV

`static/resume-en.pdf` is **committed**, because Cloudflare's Pages build image has no LaTeX
toolchain and cannot produce it. After editing `resume.tex`:

```sh
npm run cv
git add resume.tex static/resume-en.pdf && git commit -m "cv: update"
```

Requires a local LaTeX distribution (MiKTeX or TeX Live) with `pdflatex` on `PATH`. Keep
`src/lib/data/resume.ts` in step — it is the site's copy of the same content, deliberately
decoupled so the web version can be less terse than a one-page CV.

## Before you go live

A few things are deliberately left as placeholders:

- **`src/lib/data/site.ts`** — the GitHub and LinkedIn handles are guesses. Fix them or delete
  the entries; the contact page renders whatever is in the list.
- **The three posts in `src/posts/`** are starter content, marked as such in their opening
  lines. `this-blog-is-just-files` doubles as documentation for the publishing flow — worth
  keeping until you've replaced it.

### Analytics and consent

Google Analytics is on this site, and it is gated. `src/lib/consent.svelte.ts` is the only
code that may load `gtag.js`, and it does so **after** the visitor presses *Allow* in the
banner — before that there is no third-party script on the page and no request to Google at
all. This is deliberately stricter than Google Consent Mode, which loads the tag regardless
and merely tells it to behave; § 25 TTDSG is about access to the visitor's device, and the
cleanest way to not access it is to not be there.

Consequences worth knowing:

- **Declined and unanswered visitors are invisible to GA.** The numbers in the GA dashboard
  are a subset of real traffic, not a measurement of it. Cloudflare's own Web Analytics is the
  place to look for a total.
- **The `/api/event` feed counter runs for everyone**, outside the gate, because it sets no
  cookie and carries no identifier — see the header comment in `src/lib/track.ts`.
- **Withdrawal reloads the page** when consent is withdrawn in the same page load that granted
  it. `gtag.js` cannot be unloaded once it has started its own timers.
- The decision lives in `localStorage` under `consent.analytics.v1` and **expires after a
  year**, after which the banner asks again.
- Changing what GA collects means changing `src/routes/datenschutz/+page.svelte` too, and
  bumping `privacy.updated` in `src/lib/data/site.ts`. Consent is only valid for what the
  visitor was actually told.

### Fonts are self-hosted

- Fonts come from the `@fontsource-variable/*` npm packages (imported in `src/routes/+layout.svelte`)
  and are bundled into the build, so no visitor IP is sent to Google. The Datenschutz page
  says so; keep it in step if the font set changes.

## Connecting the Pages project

In the Cloudflare dashboard: **Workers & Pages → Create → Pages → Connect to Git**, pick the
repository, then set:

| Setting | Value |
| --- | --- |
| Framework preset | SvelteKit (or None) |
| Build command | `npm run build` |
| Build output directory | `.svelte-kit/cloudflare` |
| Production branch | `main` |

Name the project **`oechsner-dev`**, matching the `name` field in `wrangler.jsonc`. Since the
Wrangler file is part of the build, keep those two in sync — renaming one without the other is
an avoidable way to break the build.

Two things worth knowing about that form:

- **`pages_build_output_dir` wins.** Once a Wrangler configuration file with that key is
  deployed, "your Wrangler file is the source of truth" and the dashboard build settings are
  overridden. The dashboard still asks for the output directory at project-creation time, so
  set it to the same `.svelte-kit/cloudflare` rather than relying on one silently beating the
  other.
- **Pin Node.** The Pages v3 build image defaults to Node 22.16.0, but v2 defaults to 18.17.1,
  which is too old for this toolchain. `.nvmrc` pins it explicitly so the build doesn't depend
  on which image the project happens to get.

## Architecture notes

Everything is prerendered except one route — `src/routes/+layout.ts` sets `prerender = true`,
and the post route exports `entries()` so the prerenderer knows every slug. The output is a
folder of HTML files plus `_worker.js`.

The exception is `src/routes/blog/+server.ts`, which opts out of prerendering to return a real
301 for the retired `/blog` index. That cannot be done with a `_redirects` file: adapter-cloudflare
writes `_routes.json` with `include: ["/*"]` minus the prerendered paths, so an unmatched `/blog`
reaches the Worker before Pages ever consults `_redirects`. A prerendered `redirect()` is worse
still — it emits a 200 page with a meta-refresh.

`src/lib/posts.ts` uses an **eager** `import.meta.glob`, which bundles every post's compiled
component into the chunk that renders the list. At this scale that costs a few kilobytes and
buys a completely synchronous, flash-free render. Past roughly fifty posts the trade flips; the
fix then is a lazy glob plus a build-time metadata manifest, contained to that one file.
