# oechsner.dev

A small SvelteKit demo on **Cloudflare Pages**. The server side runs as a Pages Worker, and
Cloudflare's own Git integration builds and deploys on every push — no API tokens, no deploy
credentials anywhere.

## What's in here

| Path | Purpose |
| --- | --- |
| `src/routes/+page.svelte` | The page. Fetches `/api/hello` on mount and renders the result. |
| `src/routes/api/hello/+server.ts` | **The Worker.** A SvelteKit server route; `adapter-cloudflare` compiles it into `_worker.js`. |
| `wrangler.jsonc` | Cloudflare config: project name, compatibility date, `vars`, and `pages_build_output_dir`. |
| `worker-configuration.d.ts` | Generated by `wrangler types`. **Committed on purpose** — see below. |
| `.nvmrc` | Node version, read by both the Pages builder and GitHub Actions. |
| `.github/workflows/ci.yml` | Optional type-check on PRs and non-`main` branches. |

`pages_build_output_dir` is what puts `adapter-cloudflare` into Pages mode. With it set, the
build writes static assets **and** `_worker.js` into `.svelte-kit/cloudflare`.

## Local development

```sh
npm install
npm run dev       # Vite dev server — fast, but not the real Workers runtime
npm run preview   # builds, then serves the real _worker.js via `wrangler pages dev`
```

Use `npm run preview` when you care about the Worker. Under `npm run dev` there is no
`platform.cf`, so the page shows "not on the Workers runtime" instead of edge metadata.

## Connecting the Pages project

In the Cloudflare dashboard: **Workers & Pages → Create → Pages → Connect to Git**, pick the
repository, then set:

| Setting | Value |
| --- | --- |
| Framework preset | SvelteKit (or None) |
| Build command | `npm run build` |
| Build output directory | `.svelte-kit/cloudflare` |
| Production branch | `main` |

Name the project **`oechsner-dev`**, matching the `name` field in `wrangler.jsonc`. Since the
Wrangler file is now part of the build, keep those two in sync — renaming one without the other
is an avoidable way to break the build.

That's the whole setup. Cloudflare clones the repo, runs the build in its own CI, and uploads
the result itself — nothing is stored in GitHub secrets.

Two things worth knowing about that form:

- **`pages_build_output_dir` wins.** Cloudflare's docs are explicit that once a Wrangler
  configuration file with that key is deployed, "your Wrangler file is the source of truth"
  and the dashboard build settings are overridden. The dashboard still asks for the output
  directory at project-creation time, so set it to the same `.svelte-kit/cloudflare` and keep
  the two in agreement rather than relying on one silently beating the other.
- **Pin Node.** The Pages v3 build image defaults to Node 22.16.0, but v2 defaults to 18.17.1,
  which is too old for this toolchain. `.nvmrc` pins it explicitly so the build doesn't depend
  on which image the project happens to get. (`NODE_VERSION` as a build environment variable
  does the same job.)

**Private repositories** work fine — you grant the Cloudflare GitHub App access to the repo
during the connect flow. Note that a private repo does *not* make the deployed site private;
`*.pages.dev` stays reachable to anyone with the URL. Gate it with Cloudflare Access if that
matters.

## How deploys work

- **Push to `main`** → Cloudflare builds and publishes to production.
- **Push to any other branch, or open a PR** → Cloudflare builds a preview deployment with its
  own URL and comments it on the PR.
- **Rollbacks** are in the dashboard under the project's *Deployments* tab.

`ci.yml` is optional and independent of all this. It runs `npm run check` and `npm run build`
on PRs so type errors surface in GitHub rather than only in the Cloudflare build log. Delete it
if you'd rather have one build system — on a private repo it also draws down your Actions
minutes, whereas Pages builds do not.

`npm run check` runs `wrangler types --check` first, which fails if the committed
`worker-configuration.d.ts` no longer matches `wrangler.jsonc`. That's why the generated file is
committed: it turns "someone added a binding and forgot to regenerate types" into a build
failure rather than a runtime surprise. After editing `wrangler.jsonc`, run `npm run gen` and
commit the result.

## Configuration values and secrets

Plain-text values go in `vars` in `wrangler.jsonc` and arrive as `platform.env.SITE_NAME` etc.
They are committed to the repo, so **never put credentials there**. Real secrets go in the
dashboard under **Settings → Variables and Secrets**, or:

```sh
npx wrangler pages secret put MY_SECRET
```

They surface on `platform.env` the same way, and `npm run gen` picks both up.
