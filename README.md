# oechsner.dev

A small SvelteKit demo deployed to **Cloudflare Pages**, with the server side running as a
Pages Worker and GitHub Actions doing CI/CD.

## What's in here

| Path | Purpose |
| --- | --- |
| `src/routes/+page.svelte` | The page. Fetches `/api/hello` on mount and renders the result. |
| `src/routes/api/hello/+server.ts` | **The Worker.** A SvelteKit server route; `adapter-cloudflare` compiles it into `_worker.js`. |
| `wrangler.jsonc` | Cloudflare config: project name, compatibility date, `vars`, and `pages_build_output_dir`. |
| `worker-configuration.d.ts` | Generated by `wrangler types`. **Committed on purpose** — see below. |
| `.github/workflows/ci.yml` | Type-check + build on PRs and non-`main` branches. |
| `.github/workflows/deploy.yml` | Build + deploy to Cloudflare Pages on push to `main`. |

`pages_build_output_dir` is what puts `adapter-cloudflare` into Pages mode. With it set, the
build writes static assets **and** `_worker.js` into `.svelte-kit/cloudflare`, and
`wrangler pages deploy` picks that directory up from the config — which is why the workflow
passes no directory argument.

## Local development

```sh
npm install
npm run dev       # Vite dev server — fast, but not the real Workers runtime
npm run preview   # builds, then serves the real _worker.js via `wrangler pages dev`
```

Use `npm run preview` when you care about the Worker. Under `npm run dev` there is no
`platform.cf`, so the page shows "not on the Workers runtime" instead of edge metadata.

## One-time Cloudflare setup

**1. Create the Pages project.** Do this before the first CI run:

```sh
npx wrangler login
npx wrangler pages project create oechsner-dev --production-branch main
```

This is not optional. `wrangler pages deploy` can create a project interactively, but in a
non-interactive CI runner it hard-fails with *"The Pages project ... does not exist"* instead.

**2. Create an API token** at
<https://dash.cloudflare.com/profile/api-tokens> → *Create Token* → *Create Custom Token*:

- Permission: **Account → Cloudflare Pages → Edit**
- Account Resources: the account you're deploying to

**3. Add two GitHub repository secrets** (*Settings → Secrets and variables → Actions*):

| Secret | Where to find it |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | The token from step 2 |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard sidebar, or `npx wrangler whoami` |

## How CI/CD works

- **Pull requests and non-`main` branches** run `ci.yml`: `npm ci` → `npm run check` → `npm run build`.
- **Push to `main`** runs `deploy.yml`, which repeats those steps and then deploys with
  `wrangler pages deploy --branch=main`. Because `main` is the project's production branch,
  that publishes to production; any other branch would become a Pages preview deployment.
- `workflow_dispatch` lets you redeploy `main` by hand from the Actions tab.

`npm run check` runs `wrangler types --check` first, which fails if the committed
`worker-configuration.d.ts` no longer matches `wrangler.jsonc`. That's the reason the generated
file is committed: it turns "someone added a binding and forgot to regenerate types" into a
CI failure rather than a runtime surprise. After editing `wrangler.jsonc`, run `npm run gen`
and commit the result.

## Configuration values and secrets

Plain-text values go in `vars` in `wrangler.jsonc` and arrive as `platform.env.SITE_NAME` etc.
They are visible in the client-readable config, so **never put credentials there**. Real
secrets go in instead:

```sh
npx wrangler pages secret put MY_SECRET
```

They surface on `platform.env` the same way, and `npm run gen` picks both up.
